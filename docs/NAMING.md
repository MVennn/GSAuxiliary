# 文案与命名规范

> **一句话**：开关本身就是「启用」—— 用户拨动开关这个动作已经表达了「打开 / 增强」，
> 文案里不要再写一遍。名字只回答一个问题：**这个功能是什么**。

适用范围：`values/strings.xml` / `values-en/strings.xml` 里所有**用户可见**的文案 ——
分区名（`category_*`）、功能名（`feature_*_title` / `feature_*_switch`）、说明
（`feature_*_summary` / `feature_*_switch_summary`），以及二级菜单的标题与条目。

---

## 1. 三条硬规则

### 规则一：名称里不写「启用」「增强」

开关 / 卡片本身就是「启用」的载体，`启用 XXX` 里的「启用」是纯冗余；
整个模块就是「增强」，分区名 / 功能名再挂一个「增强」是同义反复。

| ❌ 别写 | ✅ 写成 |
|---|---|
| 启用直达标准行情 | 直达标准行情 |
| 启用自选股高亮 | 自选股高亮 |
| 策略页增强 | 策略页 |
| 股票详情页增强 | 股票详情页 |
| 显示增强 | 显示 |

同理不写：「开启」「打开」「支持」等开关本身已蕴含的动词，以及「增加 XXX **功能**」
里的「功能」二字。

### 规则二：名称里不写多余符号

用户可见文案**不用引号**（`「」`、`『』`、`《》`）、不用句末省略号、不用装饰性符号。
界面元素名直接书写；需要点明控件类型时用**半角空格**分隔（见规则三）。

| ❌ 别写 | ✅ 写成 |
|---|---|
| 启用「全选」按钮 | 增加 全选 按钮 |
| 底栏「智能盯盘」入口 | 底栏智能盯盘入口 |

> 这条只管**用户看得见的文案**。代码注释、`docs/` 文档、日志里的 `「」` 不受此限 ——
> 那里靠引号区分「界面上的名字」和叙述文字，是有用的。

### 规则三：新增的元素用「增加 + 内容 + 控件类型」

如果一个功能是在原界面上**新加**一个原本不存在的东西（按钮 / 菜单项 / 入口 / 开关 / 项），
名称写成三段式，中间用**半角空格**隔开：

```
增加 + 内容 + 控件类型
```

| ❌ 别写 | ✅ 写成 |
|---|---|
| 启用「全选」按钮 | 增加 全选 按钮 |
| 启用「筛选股票」 | 增加 筛选股票 菜单项 |
| 启用底栏「智能盯盘」入口 | 增加 智能盯盘 入口 |

- **控件类型**用词：`按钮` / `菜单项` / `入口` / `开关` / `项`。
- **内容**只写界面上的那个名字（`全选` / `筛选股票` / `智能盯盘`），
  不加页面前缀 —— 页面由**分区名**交代，重复写就是冗余。

## 2. 先判类型：这个功能是「增强」还是「新增」？

规则一与规则三的分岔点就在这里。**关掉开关，看目标 App 上少了什么：**

| 关掉开关后…… | 类型 | 名称写法 |
|---|---|---|
| 原来**就有**的东西变了（颜色 / 行为 / 布局） | **增强** | 直接写「东西」本身：`自选股高亮`、`直达标准行情`、`隐藏理财项`、`板块只留三项` |
| 原来**没有**的东西没了（多出来的按钮 / 菜单项 / 入口） | **新增** | `增加 + 内容 + 控件类型`：`增加 全选 按钮` |

一句话记：**「本来就有、被我改了」→ 名词；「本来没有、是我加的」→ 增加 XX XX。**

## 3. 三层文案，各写什么

`FeatureSpec` 里一条功能有四个文案字段，职责不同：

| 字段 | 谁看得见 | 写什么 |
|---|---|---|
| `titleRes` / `summaryRes` | **看不见**，只参与搜索匹配 | 完整功能名 + 完整说明（可带页面上下文，如「策略详情页里……」） |
| `switchTitleRes` | **卡片上的功能名**，用户唯一可见 | 按本规范起名（短、无「启用 / 增强」、无符号） |
| `switchSummaryRes` | 卡片下方那一行说明 | 一句话说清「打开后会发生什么」 |

> 界面上只渲染 `switchTitleRes` / `switchSummaryRes`（见 `ui/FeatureTab.kt` 的 `FeatureEntry`）。
> `titleRes` / `summaryRes` 目前只喂搜索 —— 但**也必须**遵守规则一 / 二，
> 否则用户按名字搜不到它。

## 4. 分区名（`category_*`）

分区名是**名词**，只交代「这一组功能作用在哪个页面 / 哪个层面」，不带「增强」：

| 资源 | 文案 |
|---|---|
| `category_login` | 登录 |
| `category_strategy` | 策略页 |
| `category_stock_detail` | 股票详情页 |
| `category_dock` | 底栏 |
| `category_home` | 首页 |
| `category_market` | 行情市场 |
| `category_display` | 显示 |

分区的**归属判据**（一个功能该进哪个分区）是另一件事，见
`ui/FeatureCatalog.kt` 顶部注释与 `docs/EXTENDING.md` 的「分区怎么选」。

## 6. 新增功能时的落地清单

1. 先按 §2 判类型，再按 §1 的三条规则写出 `switchTitle`。
2. 落到 `values/strings.xml` **与** `values-en/strings.xml`（中英同步，一条都不能少）。
3. 英文按同一套逻辑：`Enable xxx` → `xxx`；新增类 → `Add "xxx" button` / `Add "xxx" entry`
   （英文里引号是标注界面标签的排版惯例，**保留**；规则二只管中文文案）。
4. 只有**新开分区**时才动 `category_*`，并同步 `ui/FeatureCatalog.kt` 顶部注释与本文件 §4。
5. 回头看一眼 §5 的对照表，确认新名字和现有名字**读起来是一套的**。

## 7. 反例速查

| 别写 | 因为 |
|---|---|
| 启用 XXX | 开关已经说了「启用」 |
| XXX 增强 / 增强 XXX | 整个模块就是增强，分区 / 功能名不必再声明 |
| 增加 XXX 功能 | 「功能」二字冗余，直接说增加了什么 |
| 「XXX」按钮 | 用户可见文案不用引号 |
| 增加全选按钮 | 三段式要用半角空格分隔：`增加 全选 按钮` |
| 增加 自选股高亮 | 这是**增强**类（名字本来就在），不该用「增加」；直接写 `自选股高亮` |
