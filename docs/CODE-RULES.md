# 编码纪律

> **一句话**：从 2026-10-17 两轮审查的 6 高 / 10 中 / 17 低，以及 2026-10-19 的
> 注入性能排查（41 项发现）里提炼的必守规则 —— 每条都对应至少一个真实踩过的坑，
> 写新代码时按主题对照，新功能合入前过一遍 §8 清单。

问题的**修法**在 CHANGELOG 与对应 FEATURE 文档里，这里只收「规则 + 为什么 +
违反时的典型症状」，不重复实现细节。本文是编码纪律的**单一正本**。

---

## 1. Xposed 生命周期与钩子卫生

**规则 1.1 · install 与还原必须成对设计。**
每个 Feature 的 `install()` 落下的每一笔（钩子、decorView 监听、注入视图、
窗口属性、替换的 adapter），都要能被自己的 `onConfigChanged(false)` 或
卸载路径撤销。写 install 时同步写还原，不留「以后再补」。

- 症状：关了开关功能还在跑；只有第一次关生效。
- 案例：热重载僵尸实例（审查高-1）——布局回调不是 Xposed 钩子，
  `unhookAll` 摘不掉，旧实例永远等不到关闭通知。

**规则 1.2 · 热重载语义：装饰性现场必须可被「陌生人」识别。**
`onHotReloaded` 只卸钩子。挂在宿主视图上的东西（listener、注入的子视图、
改过的 LayoutParams、替换的 adapter）在新实例眼里是**无主的**——识别手段
必须在**注入时就埋下**：keyed tag、类名标记、可反射拆包的代理，三选一。
还原逻辑不得只依赖「本实例的记账表」。

- 症状：热重载后关开关关不掉；新实例对残留现场放弃治疗（页面功能死掉）。
- 案例：StgStockFilter 跨实例代理识别（类名 + 反射 `getTarget()`）、
  StockDetailBar 的 keyed tag 存原宽 + restore 兜底扫描 + syncBar 自愈。

**规则 1.2.1 · 拿「自己的类名」当判据时必须配 proguard keep，且同实例优先用身份。**
模块自己也开 R8（`isMinifyEnabled = true`），**类名标记会被混淆**——
`StgStockFilterFeature$FilteredAdapter` 在装机包里叫 `f2.m`。
用类名认自己注入的东西时：① `app/proguard-rules.pro` 补 `-keepnames`（类名）与
`-keepclassmembers`（反射要调的方法名）；② **同实例一律用身份判**（自己的记账表
/ 列表 → 代理的弱引用表），类名只当**跨实例兜底**；③ 判据失效的路径不要静默 ——
每个早退都记一条带原因的日志。

- 症状：release 包「点了没反应、重启/重进才生效」，debug 包或开发期完全不重现。
- 案例：2026-10-19 —— 策略详情「筛选股票」点「确定」不生效（要退出重进）、
  筛完点行点错股票：`"FilteredAdapter" in a.javaClass.name` 被 R8 打穿，
  认不出自己刚装的过滤代理（见 [FEATURE-STG-FILTER.md](FEATURE-STG-FILTER.md) §五）。

**规则 1.3 · 启动时跳过的功能必须保持「可补装」。**
`installAll` 会跳过未启用的功能；`onConfigChanged` 里的补装路径依赖
「Feature 没有启动期唯一性假设」。新功能的 `install()` 必须幂等友好：
不在 install 里读一次性的静态状态、不假设「一定在进程启动早期被调」。

- 症状：宿主不重启，新开的开关永远不生效（审查高-2，真机已验证补装链路）。

**规则 1.4 · 状态表一律 WeakReference + synchronized 容器。**
Activity / View / PopupWindow / WebView 的引用表用
`WeakHashMap` 或 `synchronizedList(WeakReference)`；Key 选视图本身或
decorView root，不选 position（复用会点 A 开 B）。

⚠️ **值的强引用不能反向走到 key**（listener 闭包捕获 decorView、View 的 Context
是 Activity、代理持有原 adapter、wrapper 捕获 ListView……）—— 有环时弱键等于失效，
条目永不回收。两种正确形态：
  ① 强持簿记对象、簿记内部对可能反向的视图用弱引用（`RowViews` 的写法）；
  ② 确实有环的表，必须在 `Feature.onActivityDestroyed` 里按页面身份显式删除条目。
**不要**为了断环把簿记对象本身改成弱引用 —— 它没有别的强引用时会被立刻 GC，
注入/缓存直接停掉（2026-10-20 `9221365` 踩过）。

- 症状：Activity 泄漏、长时间使用后卡顿；列表复用后点错条目。

## 2. 热路径（每行 / 每帧 / 每次布局回调）

**规则 2.1 · 反射结果必须按类缓存。**
`getView`、布局回调这类高频路径里，`Reflect.findMethod/findField` 的结果
必须进 `WeakHashMap<Class<*>, 缓存对象>`（适配器类与条目类分两张表），
**解析失败也要缓存**，否则每行重扫整条继承链。
值**对实例不变**的（如条目上的「代码.市场」）再按**实例**缓一层 ——
同一只股票在滚动里会被反复重绑，反射一次就够。

- 症状：列表滚动掉帧、GPU 没满 CPU 满。
- 案例：WatchlistFeature 每行全候选扫描（审查高-6）；StgStockFilter 每行
  `getItem` + 8 个字段候选 + 每次刷新对全量重扫（2026-10-19 加按类/按实例缓存）。

**规则 2.2 · 计算型 getter 不得出现在热路径上。**
会被每行 / 每帧读取的属性（如 `ConfigSnapshot.fingerprint`）必须构造期
一次算好存字段，不得 `get()` 里做 O(n) 哈希（方案 JSON 可达几十 KB）。

**规则 2.3 · 高频回调要限速，但**只能延后、不能丢弃**。**
布局回调驱动的 sync：连续认不出来时按 `layoutThrottleMs` 限速；本轮真动了视图
（用 mutations 计数判断）之后的 `actionCooldownMs` 窗口内把回调汇总成一趟。
**两条都走 `deferSync` 排到稍后补跑，绝不 `return` 掉这一趟。** 窗口长度只由
「用户感知不感知得到」决定（200ms ≈ 12 帧）；压爆发的收益来自「同一窗口只跑一趟」，
与窗口多长无关。入页首次同步不过闸。

- 为什么：布局回调是「页面变了」的**唯一**信号，而宿主恰恰在我们改完视图之后
  立刻布局一趟 —— 新建的分页、重建的底栏、补挂上去的子视图都在那一趟里上来；
  丢掉它，界面就停在这一轮的样子，要等某次与本功能无关的布局才补上。
- 症状：改动要停留一会儿才生效 —— 「个股详情页滑过去不注入『智能盯盘』入口，
  要停留一会儿才出现」「底栏『理财』先消失、占位过一会儿才归位」。
- 案例：3.2.0 的 1.5 秒动作冷却（二轮审查 M4 引入，冷却期内直接跳过）在真机上
  就是这两个症状；三轮只给 `DockCleanFeature` 补了 `needsFollowUp` 一条，
  其他功能照样中招（2026-10-19 BUG1）。现在冷却=限速：**延后不丢弃 + 200ms**。
- 多趟状态机（`DockCleanFeature` 的四招重排）覆写 `needsFollowUp` 让窗口整体让路，
  但那条钩子**只管手感、不管正确性** —— 忘了覆写最多慢 200ms，不会再「停在中间态」。

**规则 2.4 · 录制型 Modifier 必须条件挂载。**
`layerBackdrop` 这类每帧采样的修饰符，消费方不存在时（非玻璃模式）不得
常驻；过渡动画期（淡出 alpha>0）也算消费，条件里要盖住。

- 案例：一级页漏挂条件、dock 淡出期闪变（审查中-5）。

**规则 2.5 · 热路径上的日志先问等级、再拼字符串。**
Kotlin 的字符串模板在**调用前**求值：`GLog.d("…${x}…")` 即使被等级挡掉，
那份字符串（以及插值里的 `toString`、资源名反查）也已经造出来了。
每帧 / 每次布局回调 / 每行上的日志写成 `if (GLog.isDebug) GLog.d(…)`
（INFO 档用 `GLog.isInfo`）。

- 症状：滚动手势里稳定产生垃圾（每趟一两个 String，带 `getResourceEntryName`
  的还多一次资源表反查），把等级调到「关闭」也省不掉。
- 案例：PageSyncFeature 限速窗口内的每趟日志、ViewPatcher.describe（2026-10-19）。

**规则 2.6 · 每帧 / 每次回调的固定开销要合账：状态合成一个对象、一趟一次锁。**
「每页 N 张 `synchronizedMap(WeakHashMap)`」各自看着便宜，但它们在**每一帧**
都要各抢一次锁、各做一次表操作，而且 `Long` 进 Map 必然装箱。按页面
（`decorView`）把状态收进**一个对象**、放进一张弱表，一趟只查一次、锁一次，
字段用原生类型；快路径上的「清零」也要先看有没有账可清。

- 症状：滚动 / 动画期 CPU 不是花在功能上，而是花在「查状态」上；帧时间随功能数线性涨。
- 案例：PageSyncFeature 的 12 张状态表（2026-10-19 合并成一个 `PageState`）、
  首帧屏障快路径原来每帧无条件写两张表。

**规则 2.7 · 高频挂点里先判目标、再取参数。**
`XposedInterface.Chain#args` 会把整条参数表**物化成一个 List**；而挂在基类上的钩子
（`BaseQuickAdapter#getView` 这类）收到的是**全 App 所有列表**的每一行。
先用 `thisObject` 的类名做最便宜的判据，命中后再用 `getArg(0)` 取那一个参数。

- 症状：非目标列表的每一行都在白付一次 List 物化（外带用不到的装箱）。
- 案例：筛选 / 自选高亮的 `getView` 钩子（2026-10-19）。

## 3. 日志与隐私

**规则 3.1 · INFO 及以上日志不得出现完整「6位代码.市场号」与含代码的 URL。**
个股代码过 `maskStockCode()`（保留前 2 位）或降 DEBUG；失败日志报状态码，
不带完整 URL。这条是硬性口径，贴日志是用户求助的主要方式。

**规则 3.2 · 注释措辞不得与免责声明 §8 矛盾。**
不写「伪装 / 规避风控 / 绕过检测」类措辞——注释是白纸黑字的意图证据。
UA 用常规浏览器形态，注释只说技术原因（行情接口对非浏览器 UA 拒答）。

**规则 3.3 · 「点了没反应」的每一处早退都要能自证原因。**
功能链路上有大量 `return`（找不到列表 / 适配器不是目标 / 数据还没到…）。全静默时
用户看到的只有「点了没反应」，日志里一行都没有 —— 只能靠临时加日志、重编、装机去猜。
每处早退给一条**带原因**的日志（同一原因去重，别刷屏），用户导出的日志里直接能看出卡在哪。

- 症状：报障是「按钮没反应」，日志干干净净，排查要先加诊断再重编。
- 案例：`ensureClickRemap` 的 `noteSkip`（2026-10-17 加，当天就定位了问题）；
  `applyFilter` 的 `noteApplySkip`（2026-10-19 加，当场定位「筛选确定不生效」）。

- 案例：HttpTransport 旧注释与 DISCLAIMER §8 正面冲突（审查高-1，法律专项）。

## 4. JS 桥与注入脚本

**规则 4.1 · 桥的每个方法都要 URL 守卫。**
自建桥挂在宿主全部 WebView 上，页面内第三方脚本可调。除 apply 外，
新增的任何带副作用的桥方法（saved / manage / 未来的）一律先
`pricePageGuarded()` 校验，不通过直接 return。

**规则 4.2 · 调试口必须限频 + 截断。**
diag 类方法：单条 200 字符 + 1 秒 1 条，时间戳放外层类（每个 WebView 各一个
Bridge 实例，放 Bridge 里限不住全局）。

**规则 4.3 · Kotlin 裸串里的 JS：改动后真机验证。**
`$xxx` 要写 `${'$'}xxx`；任何 JS 改动都要在真机 H5 页面过一遍
（转义错了是运行时才炸，编译不报）。保守改法：不引入新的 `$`。

## 5. 数据与缓存

**规则 5.1 · 缓存 key 必须含全部影响结果的参数。**
日 K 缓存 key 漏了 n 维度 → 长短回扫混用时重复请求（审查中-7）。
新缓存设计时列全「哪些参数变了结果就变」，一个都不能少。

**规则 5.2 · 会话 memo 与通道缓存分层。**
会话内防重复（HashMap memo）管「同一会话点两下」，通道 TTL 缓存管
「跨会话复用」；失败结果不进 memo（要允许重试）。

**规则 5.3 · LSPosed remote prefs 的写路径保持 commit。**
`edit()` 换 `apply()` 的推送语义未验证过，**不要顺手优化**（审查低-9 明确不改）。

## 6. 依赖与构建

**规则 6.1 · 升级任何带 Compose/AAR 元数据的库，先跑 `checkDebugAarMetadata`。**
Miuix 0.9.4 实测被 `minAgpVersion = 9.1.0` 硬拦（Compose 1.12.0 全家桶），
`dependencies` 任务通过≠能构建。版本矩阵与案例见 [BUILD.md](BUILD.md) §为什么钉死。

**规则 6.2 · compileSdk / AGP / Miuix 三者是绑定关系**，单独动一个会连环炸，
联动调整前读 [BUILD.md](BUILD.md) 的版本矩阵一节。

## 7. 仓库与 git 纪律（对维护者）

**规则 7.1 · `reset --hard` 前必须 `git status`。**
工作区常有并发会话的在途改动；脏树切历史用
`git update-ref refs/heads/main origin/main`（树内容相同时 index 仍有效），
**绝不**带脏树 reset。

**规则 7.2 · `git add -A` 后必须 `git status` 复核再 commit。**
`.work/` 归档曾被 add -A 误提交进公开仓库，直接导致多一轮历史重写。

**规则 7.3 · 历史重写（filter-repo）后必须独立终验。**
用另一个子代理/会话从远端拉 zipball 与 API 实测，不能只看本地
`git log`——第一轮清洗漏掉的 `.work` 副本就是自己验自己漏掉的。

**规则 7.4 · 敏感路径只进 `.work/`（gitignored）**，归档移动用
`git mv` 后立刻 `git status` 确认目标路径没进暂存区。

## 8. 新功能合入前自检清单

1. install 落下的每一笔都有对应还原路径？（§1.1）
2. 注入的视图现场有 keyed tag / 类名标记，热重载后新实例能识别？（§1.2）
   用类名当判据的，proguard 里有对应 `-keepnames` / `-keepclassmembers`，
   且同实例走身份判、早退有日志？（§1.2.1）
3. install 不依赖启动期唯一性，运行中补装能生效？（§1.3）
4. 状态表全是弱引用 + 同步容器？（§1.4）
5. 高频路径无未缓存反射、无计算型 getter？（§2.1/2.2）
6. 布局回调 sync 的限速是「延后不丢弃」？多趟状态机覆写 `needsFollowUp`？（§2.3）
7. 热路径日志先问了等级再拼字符串？（§2.5）
8. 每帧 / 每次回调的状态是「一个对象 + 一趟一次锁」？（§2.6）
9. 挂在基类上的高频钩子先判目标、再用 `getArg(i)` 取参数？（§2.7）
10. INFO 日志无完整股票代码 / URL？「点了没反应」的早退都有原因日志？（§3.1/3.3）
11. 新桥方法有 URL 守卫 + 限频？（§4.1/4.2）
12. 缓存 key 参数列全了？（§5.1）
13. 动过文档的话，DISCLAIMER / NAMING / 版本号口径是否按
    [MAINTENANCE.md](MAINTENANCE.md) §3 联动？
