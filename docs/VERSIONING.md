# 版本命名规范

> **一句话**：有没有「功能更新」决定动哪一位 —— **有功能更新进次版本（+0.1.0），
> 没有就进补丁版本（+0.0.1）**。

适用范围：`app/build.gradle.kts` 里的 `versionName`，以及发版 tag、Release 命名。
`versionCode` 不参与命名，只做递增计数（见 §3）。

---

## 1. 三段式与进位规则

`versionName` 是三段式：`主版本.次版本.补丁版本`（如 `2.17.2`）。

| 这次发版包含…… | 动哪位 | 写法 | 例子 |
|---|---|---|---|
| **没有功能更新** —— 只修 bug、调文案 / 样式 / 布局、改文档、动构建脚本 | **补丁版本 +0.0.1** | `x.y.z` → `x.y.z+1` | `2.17.1` → `2.17.2` |
| **有功能更新** —— 新增功能、现有功能的行为 / 交互变了、功能被移除 | **次版本 +0.1.0**，补丁归零 | `x.y.z` → `x.y+1.0` | `2.17.2` → `2.18.0` |
| 重大重写、不兼容变更（配置格式不兼容、最低安卓版本要求提高等） | **主版本 +1.0.0**，后两段归零 | `x.y.z` → `x+1.0.0` | `2.18.0` → `3.0.0` |

进位是**连锁**的：次版本进位时补丁必然归零（`2.17.2` 的下一次功能更新是
`2.18.0`，不是 `2.18.1` 也不是 `2.17.3`）；主版本进位时后两段都归零。

## 2. 怎么判断「有没有功能更新」

判断口诀：**打开模块的「功能」页找答案 ——**

- 用户能在功能页 / 各二级菜单里**找到一个以前没有的东西**（新开关、新设置项、
  新入口），或者某个现有功能**关掉再开效果不一样了** → 有功能更新 → `+0.1.0`；
- 功能页翻遍也找不到任何新东西，改的是「做得对不对」（修复）与
  「长得好不好」（文案 / 颜色 / 间距 / 图标）→ 没有功能更新 → `+0.0.1`。

两个边界情况：

| 情况 | 算不算功能更新 | 理由 |
|---|---|---|
| 修一个功能「开了没效果」的 bug | ❌ `+0.0.1` | 行为回到了它本来该有的样子，不是新行为 |
| 删掉某个功能或某个设置项 | ✅ `+0.1.0` | 功能列表变了，用户可感知的减法也是更新 |
| 新增 / 删除一个分区、给功能改名 | ✅ `+0.1.0` | 功能页的结构变了 |
| 只改模块 App 界面（概览 / 设置 / 关于页） | ❌ `+0.0.1` | 功能页没有变化；模块 App 的观感调整按样式处理 |

拿不准时问一句：**写 Release 说明时，会不会出现「新增 / 变更 / 移除了某功能」
这样的句子？** 会 → `+0.1.0`；全文只有「修复 / 优化」→ `+0.0.1`。

## 3. versionCode

- `versionCode` 与版本命名**无关**，只保证**每次发版严格 +1**（LSPosed /
  Android 用它判断新旧，回退会被拒绝覆盖安装）。
- tag 格式为 `{versionCode}-{versionName}`（如 `42-2.17.2`），
  由 `release.yml` 校验一致性，见 `docs/RELEASE.md`。

## 4. 落地位置

发版前改两处（`docs/RELEASE.md` §3 的发版前检查会复核）：

```kotlin
// app/build.gradle.kts → android.defaultConfig
versionCode = 42      // 严格 +1
versionName = "2.17.2" // 按 §1 进位
```

同时在 `CHANGELOG.md` 顶部补该版本的段落，并注明这版走的是哪一档
（有 / 无功能更新），方便回看进位是否守规矩。
