# 手势导航条同色（`nav_bar_blend`）

> 让屏幕底部那条**手势导航条（小白条）**填充与紧邻界面一致的颜色，
> 而不是深色模式一条纯黑、浅色模式一条纯白。
>
> 代码：`feature/navbar/`（`NavBarBlendFeature` 调度 / `NavBarTint` 取色与上色 /
> `NavBarTargets` 调参常量）。

---

## 1. 现象与根因

### 1.1 现象

打开金太阳，屏幕最下面那一条是这样：

| 模式 | 小白条区域 | 与上方界面的关系 |
|---|---|---|
| 浅色 | 一片纯白 | 上面是白色底栏时看着还行；底栏一有颜色就是一刀硬切 |
| 深色 | 一片纯黑 | 上面是深灰 / 深蓝底栏时同样一刀硬切 |

既不跟随上方界面的颜色，也没有任何过渡。

### 1.2 根因：那块区域是**宿主的窗口自己画的**，不是系统画的

宿主 targetSdk **30**（见本地参考数据 apk-analysis-report.md），全程非沉浸 ——

- 没有 `setDecorFitsSystemWindows(false)`；
- Android 15 的「targetSdk 35+ 强制沉浸」也轮不到它。

于是屏幕被切成三块：状态栏 / **宿主内容** / 导航条。导航条那一块不属于内容区，
由 `DecorView` 按 `window.navigationBarColor` 自己填：

```
DecorView（整窗高度）
├── 内容根（内容区，被系统栏 inset 让开）
└── mNavigationColorView（底部 navBarHeight 高，填 navigationBarColor）
```

而宿主**没有设 `navigationBarColor`**（或设成了透明），于是 `DecorView` 落回
主题的 `android:windowBackground` —— **深色模式纯黑、浅色模式纯白**。
这就是那条硬边的全部来源。

顺带一个加重因素：**`navigationBarContrastEnforced` 默认是开的**。
系统为了保证金太阳那条小横杠一定看得见，会在透明导航条上叠一层半透明遮罩，
观感就是「灰蒙蒙的一条」。模块自己的设置界面在 2.5.0 踩过完全同一个坑，
根因分析见 `docs/UI-HISTORY.md` §11.1。

### 1.3 为什么不是「宿主 API 受限」

不是。宿主只是**没做适配** —— 它既没设 `navigationBarColor`，也没关强制对比度，
更没有做沉浸。这些都是标准公开 API，模块侧完全可以从外部补上。

---

## 2. 为什么不做「真沉浸」

真沉浸 = `setDecorFitsSystemWindows(false)`，让内容一直铺到屏幕物理底边，
再给内容补 `navBarHeight` 的 bottom inset。效果最好，但代价是：

| 风险 | 说明 |
|---|---|
| 底栏会被推到小白条下面 | 主界面底栏原本就在内容底部，一旦不避让就压在横杠上，必须再给它补 inset |
| 宿主自己的 inset 处理会打架 | 页面里的 `fitsSystemWindows` 视图、`CoordinatorLayout` 行为、`WindowInsets` 监听都会同时收到新的 inset，容易算两遍 |
| 键盘 / 弹层 / 全屏页一起受影响 | 沉浸是**窗口级**开关，不是一个页面开关，改动面远超一条小白条 |
| 回滚成本高 | 出问题只能整体关掉，没有中间态 |

收益只是「底部那条融进去」，风险却是整个 App 的布局。
**不成比例。** 所以本功能只做一件事：**改 `navigationBarColor` 这一个窗口属性**。

代价也说清楚：那条区域仍然是**一块纯色**，只是这块纯色现在与紧邻界面一致。
如果上方内容是渐变 / 图片 / 圆角卡片，交界处仍可能有可见色差 —— 这是简单方案的固有边界，
不是 bug。

---

## 3. 方案

### 3.1 取色带画在哪（命门）

```
┌──────────────────────────┐
│  状态栏                   │
├──────────────────────────┤
│                          │
│  宿主内容                 │
│                          │
├──────────────────────────┤ ← decor.height − navBarHeight   ← 取色带下沿
│  ██ 取色带 3dp 高 ██      │ ← 取的就是这一行的真实颜色
├──────────────────────────┤
│  小白条（DecorView 填色）  │ ← 我们把这里换成上面取到的颜色
└──────────────────────────┘
```

**取色带必须落在内容最后一行，不能落在导航条里。**
`decorView` 是整窗高度（导航条那一块也是它的孩子），所以必须先减掉
`navBarHeight`（`rootWindowInsets` 的 `navigationBars` bottom，API 30+；
`stableInsetBottom` 兜底）。减错了就会取到**自己上一次填进去的颜色**，
自我循环、永远不变 —— 这是实现时最容易踩的一个坑。

### 3.2 上色的三件事（只改颜色是不够的）

| # | 动作 | 位置 | 不改会怎样 |
|---|------|------|---|
| 1 | `window.navigationBarColor = 取到的颜色` | `NavBarTint.paint` | 那一块仍是主题底色 |
| 2 | `window.isNavigationBarContrastEnforced = false`（API 29+） | 同上 | 系统叠一层半透明遮罩，「生硬」的一半来自这里 |
| 3 | 按亮度设 `appearanceLightNavigationBars` | `NavBarTint.setLightNavBar` | 关掉遮罩后横杠明暗全由它决定，不设会出现「白横杠压在白底上」 |

第 3 条的判据是**填进去的颜色**的亮度，不是系统深色开关 ——
用户可能把金太阳强制成深色而系统是浅色（模块设置界面踩过同款，见 `docs/UI-HISTORY.md` §11.3）。

**三键导航的例外**：三键模式下那一条是真系统栏、上面有按键，
关掉强制对比度可能让按键看不清。所以检测到非手势导航时**只改颜色、保留强制对比度**
（模式取自系统资源 `android:integer/config_navBarInteractionMode`：0/1 = 三键/两键，2 = 手势）。

### 3.3 取色三档

| 档 | 手段 | 特点 |
|---|---|---|
| ① **结构合成** | 沿「取色带覆盖链」从 `decor` 逐层下钻，把每层背景色按 alpha 合成 | **同步**、零分配、首帧就能给结果 |
| ② **像素校准** | `PixelCopy` 拷内容最后一行真实像素取平均 | **异步**、是屏幕上的真值，能救渐变 / 图片 / 圆角 |
| ③ **兜底** | 主题 `android:windowBackground` 当合成底色 | ①②都拿不到时至少不是黑 / 白硬块 |

**① 的下钻规则**：每一层只挑「覆盖取色带、且宽度 ≥ 父容器 55%」的那个子视图。
理由是底栏一行六格并列，每格只占 1/6 宽、还可能带自己的选中态底色 ——
往深钻会取到某一格的颜色；**代表「周边界面」的是整行**，所以窄子视图一律不再下钻。

**单个 `Drawable` 怎么取色**：`ColorDrawable` 直接取；其余一律**渲染成 1×1 位图**
再读那一像素（`NavBarTint.drawableColor`）。这样 `GradientDrawable` / `ShapeDrawable` /
`LayerDrawable` / `StateListDrawable` / 九宫格都能拿到一个说得过去的值，
**不用去反射各个安卓版本里名字还不一样的私有字段**。

**② 的两道闸**：

- 节流 `2000ms` + 每窗口最多 `3` 次 —— `PixelCopy` 是跨进程拷 Surface，
  且在**部分机型 / 没有 backing surface 的窗口上恒失败**，失败就认了，绝不无限重试；
- 与当前颜色的最大通道差 ≤ `24` 就不落地 —— 省掉无意义的窗口属性刷新。

### 3.4 什么时候改

| 时机 | 作用 |
|---|---|
| `Activity.onResume` | 挂上布局回调 + 立刻试一次（从别的页面返回时不用等下一次布局）。**此刻 `decorView` 还没 attach，量不出尺寸**，所以它不是落地点 |
| `ViewTreeObserver.OnGlobalLayoutListener` | **真正的落地点**。它发生在**这一帧画出来之前**，所以首帧就已经是最终颜色，用户看不到中间态。限速时**只延后、不丢弃**（同 `PageSyncFeature` 的结论） |
| `Activity.onConfigurationChanged` | 深浅色切换 / 转屏时宿主不一定重建页面，这时主动作废「主题底色」与「已应用的颜色」重算 |

每个 `Activity` 有自己的窗口，所以**每个页面都要各来一遍**。

### 3.5 关掉开关立刻还原

`onConfigChanged` 里对每个窗口恢复原样的 `navigationBarColor` / 强制对比度 / 横杠明暗，
并摘掉布局回调。原值在第一次碰到该窗口时记下（`WinState`）。

## 4. 需要验证的场景

功能开关出厂默认关；**从「关」改成「开」要重启一次金太阳**（LSPosed 在启动时装钩子）。

### 4.1 深色 / 浅色模式（各走一遍）

金太阳自己的「深色模式」开关与系统深色开关**是两个独立开关**，组合出四种情况：

| # | 系统 | 金太阳 | 期望 |
|---|---|---|---|
| 1 | 浅色 | 浅色 | 小白条 = 浅色底栏的颜色，与底栏浑然一体 |
| 2 | 深色 | 深色 | 小白条 = 深色底栏的颜色，不再是一条纯黑 |
| 3 | 浅色 | 深色（App 内强制） | 小白条跟随**金太阳**的深色，不是系统的浅色 |
| 4 | 深色 | 浅色（App 内强制） | 小白条跟随**金太阳**的浅色 |

第 3 / 4 条是最容易出错的 —— 它们验证「横杠明暗按填进去的颜色算，不按系统开关算」。

**切换过程也要看**：在金太阳里切一次深浅色（或系统切一次），
看小白条是**跟着变**还是停在旧颜色 → 验的是 `onConfigurationChanged` 那条腿。

### 4.2 页面覆盖

| 场景 | 期望 |
|---|---|
| 主界面（首页 / 行情 / 自选 / 交易 / 账户） | 每个 Tab 底部颜色不同时要各自跟上；切 Tab 后不应残留上一个 Tab 的颜色 |
| 个股详情页 | 底部若有深色买卖栏，小白条应跟随它，而不是跟随主界面 |
| 冷启动（启动图 → 主界面） | 从启动图过渡过去看到的**就是最终颜色**，不应先黑一下再变 |
| 二级页 / 弹层 / 对话框式 Activity | 悬浮窗口跳过（`window.isFloating`），不应报错 |
| 从别的 App 切回来（`onResume`） | 颜色没有丢失 |

### 4.3 手势 vs 三键

| 模式 | 期望 |
|---|---|
| 手势导航 | 彻底融入，横杠清晰可见（深色底 → 浅色横杠，反之亦然） |
| 三键导航 | 颜色跟随，**按键始终清晰可见**（保留强制对比度） |

### 4.4 关掉开关

关掉开关 → 小白条**立刻**回到原样（纯黑 / 纯白），不需要重启金太阳。

### 4.5 怎么看日志

```bash
adb shell su -c "grep nav_bar_blend /data/adb/lspd/log/modules_*.log | tail -50"
```

正常会看到类似这些行（按出现顺序）：

```
已挂 N 个 Activity 回调
结构取色 #FFFFFFFF → MainAct 导航条已同色
像素校准 #FFF7F7F7 → MainAct 导航条已同色
```

两种异常都**不是功能坏了**：

- `PixelCopy 返回 <非 0>` / `PixelCopy 不可用` —— 该机型拷不了 Surface，
  结构取色的结果继续生效（`NavBarTargets.PIXEL_MAX_TRIES` 次之后不再重试）；
- `解析不出主题底色` —— 该页面的主题没声明 `windowBackground`，等像素取色兜底。

## 5. 已知边界

| 边界 | 说明 |
|---|---|
| 那条区域仍是**一块纯色** | 上方是渐变 / 图片 / 圆角卡片时，交界处可能有可见色差。这是「只改一个窗口属性」的固有代价 |
| 页面切换没有过渡动画 | 每个 `Activity` 有自己的窗口，颜色随窗口切换瞬间变化。要做过渡得自己插一个 `ArgbEvaluator` 动画，暂未做 |
| `PixelCopy` 不是所有机型都可用 | 有结构取色兜底，只是这类机型上拿不到渐变 / 图片的精确值 |
| 状态栏不在本功能范围内 | 顶部那条是另一个窗口属性（`statusBarColor`），宿主在状态栏上的表现是另一回事 |
