# release-notes/

放**面向用户**的 Release 说明，文件名 = `versionName`：

```
docs/release-notes/2.14.0.md
```

`.github/workflows/release.yml` 发版时会找 `docs/release-notes/<versionName>.md`，
找到就用它当 Release 说明；找不到就退回 CHANGELOG 的对应段落（并在日志里
`::warning::` —— 那段是写给开发者的，用户看到的是噪音）。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / crash 栈 / 验证表格。
Release 说明是**给用户看的**，要短、写成清单、只讲「我现在能拿到什么」。两者受众不同，
不能一份两用（见 `docs/RELEASE.md` §2）。

## 形状

**清单，不是文章。** 开头一句加粗说清这版是什么，`## 本版内容` 下按分区一行一条，
最后是固定尾巴。

```markdown
**智能盯盘新增价格页一键配置等一批功能，修掉取数失败；设置页可一键导出日志。**

## 本版内容

**智能盯盘**

- 新增 价格页一键配置 —— 功能页 → 智能盯盘；价格页保存按钮右侧，按方案自动填入涨到、跌到。
- 新增 最近前高、最近前低 —— 取值项取现价上方、下方最近的波段点。

**修复**

- 修复 取数失败 —— 从个股详情页进入价格页时取不到数据。

**设置页**

- 新增 日志导出 —— 设置 → 日志；导出模块与金太阳两个进程的日志。

---

需要 root + LSPosed（支持 API 102），适配国信金太阳 8.6.0 / Android 8.1+。
安装步骤见 [README](https://github.com/MVennn/GSAuxiliary#安装)。

---

> 风险提示：本模块仅供学习研究，会 Hook 国信金太阳，可能违反其用户协议并导致
> 账号风控或封禁；不构成任何投资建议。下载使用前请阅读并同意
> [免责声明](../../blob/main/docs/DISCLAIMER.md)。
```

结尾那两行加风险提示段是**固定尾巴**，每版照抄不动。风险提示段按
[RELEASE.md §2](../RELEASE.md) 的模板**逐字粘贴、不随版本改写**（法律留痕：
持续提示、提示在先），它是固定尾巴的一部分，**不算重复内容**。

### 一条怎么写

```
新增 / 调整 / 修复 / 优化 + 功能名 —— 入口；一句话功能
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对）、优化（性能 / 稳定性 / 整理类）；另有「移除」用于删功能。
  都写全称 —— 单字「修」读着不像词。
- **功能名照抄功能页**（卡片标题 / 开关名），不加引号书名号，也不另起一个说法。
- **入口**写用户点得到的位置：「功能页 → 智能盯盘」「设置 → 日志」；不需要找入口的
  （列表里一眼能看见），改写场景（「我的盯盘列表」）。
- **功能**一句说完，写用户拿到什么。不写怎么用、不写为什么、不写「点一下就会…」。
- 说人话。「不做沉浸」「窗口属性」「强制对比度」这类只对开发者有意义的词别写；
  真要交代限制，写用户看得见的后果（「上方是渐变时交界处可能有一点色差」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 覆盖率红线（3.2.0 起）

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一（新增 / 调整 /
修复 / 优化），一行一条。没有例外：

- 代码审查的发现与修复 → 并进「修复」分组，一行写「修了什么 + 用户可见的后果」
- 性能优化 → 并进「优化」分组；同类多项可归并成一行，但要列出对象
- 纯重构（行为零变更）→ 一行「优化 代码整理 —— ……，行为零变更」
- 文档 / 法律类（免责声明、第三方声明等）→ 并进「界面」或对应分组，照写

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处用户可感知改动，
Release 说明里都得能找到对应行**。性能与审查类不另开长段落叙事 ——
那段叙事留在 CHANGELOG，Release 说明只要一行短句。

### 篇幅

- 覆盖率红线优先于篇幅：先保证**一条不漏**，再谈合并。
- 分组按功能页分区走（智能盯盘 / 行情市场 / 界面 / 设置页），不按轻重排。
- 合并手法：同分区的界面打磨（间距、对齐、动画）并成一行；
  性能同类项归并成一行但列出对象；审查修复写用户可见后果，不写根因长文。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」「你可以在…里改」「想换的话…」） | 用户要的是有什么，不是操作步骤；步骤归 README |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、取数口径、字段来源 | 同上 |
| 开关默认开还是关、改完要不要重启 | 通用信息，不随版本变 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状（「取不到数据」），其余不写 |
| 「本版没有破坏性变更，直接覆盖安装」 | 没变更就不用声明；**有**的时候才必须写 |
| 凑数的「注意」区块 | 见下 |

## 「注意」区块：能不写就不写

只在**用户不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 包名变了、要卸载重装、配置会丢。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 例如某开关实际只做到一半。如实写一条，
  免得被重复报（2.15.1 就这么做过）。
- ❌ 每版都一样的操作提醒、性能说明 —— 不写。风险提示**例外**：
  每版说明末尾固定附风险提示段（按 [RELEASE.md §2](../RELEASE.md) 模板逐字粘贴），
  属固定尾巴，不算重复内容。

## 改已经发出去的说明

`publish.py` 对已存在的 Release 走 `PATCH` 更新，同名 APK 会先删再传，不会报
`already_exists`。改完文案直接重跑一次就覆盖线上了：

```bash
python tools/publish.py --skip-build --notes docs/release-notes/<vn>.md
```

写完 `docs/release-notes/<vn>.md`、把 `versionCode` / `versionName` 递增、
推一个同名的 tag（`<versionCode>-<versionName>`），CI 就会自动发版。

> 注意：`docs/**` 在 CI 的 `paths-ignore` 里 —— 改说明文件本身不会触发构建，
> 但**打 tag 一定会触发 Release 工作流**（tag 事件不受 `paths-ignore` 影响）。
